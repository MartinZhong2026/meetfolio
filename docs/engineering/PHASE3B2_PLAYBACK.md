# Phase 3B2 — segment audio playback

In the native desktop app, open an interview's **Review** stage and click linked transcript text to hear its original audio. The player shows the segment number, elapsed time, duration and state. Pause/Resume keeps the media position; Stop releases it. Clicking the same text replays from its beginning; selecting another segment switches recordings. Text edits preserve the original audio identity and file times. Legacy/manual/demo text without audio remains editable.

## Audio and security contract

- The sandboxed renderer requests `{ interviewId, recordingId, startMs, endMs }` through the trusted main-frame preload API. It cannot supply a path. Native session metadata must associate that recording with the requested interview. Knowledge of a recording UUID alone does not authorize access from a different interview. The notebook and current interview selection are renderer-owned; this is a single-profile desktop boundary, not multi-user authentication against a compromised renderer or operating system.
- Main opens only a finalized, validated own-format WAV under the profile's recordings directory, read-only. It rejects linked roots/directories/files, wrong owners, active captures, incomplete/corrupt headers, invalid ranges and missing files. Interrupted partials must first be explicitly recovered in **Local storage & backup info**. Recovery and original recording formats are unchanged.
- Audio time comes from the segment's optional `audio` reference, **not** the interview clock. At 16 kHz mono PCM16, boundaries round to the nearest sample (1/16 ms). End is exclusive; zero-sample or out-of-file slices fail instead of silently playing other evidence.
- A new random capability exposes only the selected slice as a virtual WAV at `meetfolio://app/recording-playback/<token>`. It contains a generated header and original PCM samples; it never rewrites the source. Responses support single byte ranges, suffix ranges and HEAD with correct lengths, 206/416 and `no-store`. Invalid or released tokens return 404. Size/mtime changes detected after preparation return 410; read failures become playback errors. Moving/deleting an already open file can leave the existing OS handle readable until release; a new open requires the file to exist at its managed location.
- Native response reads are at most 64 KiB, with stream backpressure and one active response per capability. Open operations are serialized; only the latest rapid selection wins. JavaScript never loads or decodes an entire recording. The browser media engine handles progressive WAV decoding; the custom scheme enables `stream: true` as required by [Electron's protocol documentation](https://www.electronjs.org/docs/latest/api/protocol/). Browser/OS buffers are managed by Chromium; the bound applies to application reads/queues, not total process RSS.
- New selections revoke prior capabilities. Stale UI cleanup cannot revoke the new one. Stop, end, errors, review unmount, renderer navigation/crash and host shutdown release streams/handles. Beginning capture also releases playback to prevent feedback. Main refuses new playback while capture starts/runs. Async UI results after Stop/unmount are released without playing.
- Errors are shown without filesystem paths. Missing WAVs, wrong interview ownership, corruption and invalid timestamps leave notebook text editable. No audio upload, network dependency, new database schema or destructive migration is introduced.

## Verification

`npm run verify` includes native filesystem tests and playback controller tests. Native tests cover exact sample bytes, Range/HEAD/errors, wrong interview and traversal rejection, corruption/partials, rapid selection/revocation/abort, source preservation and a 1 GiB sparse-file bounded-read check. Controller tests cover progress/pause/resume/end, delayed requests, Stop/unmount, stale events, edited/legacy text and playback failures.

After `npm run build:electron`, run `node desktop/scripts/playback-smoke.mjs`. It uses actual Electron, the sandboxed preload, the custom protocol and Chromium audio playback with generated tones in a fresh ignored profile. It checks sample/range bytes, progress, pause/resume, switching/end/stop, wrong-owner/missing audio, text edits, review unmount, reload revocation and unchanged source hashes. It can also run against an unpacked app with `--executable <path>`. It does not establish physical speaker output, microphone quality, long-session stability or installation acceptance. CI runs it in the existing Windows Native job for source and unpacked builds and uploads only status reports. The existing X-ASR/WAV recovery regressions remain required.

## Backup and rollback boundary

Schema-1 notebook JSON still preserves recording UUID and file-relative times, but contains no WAV. Restoring JSON creates interview copies; their new IDs intentionally fail native ownership checks against original recordings. Export WAVs separately and retain the original profile. Do not change native metadata to bypass this check. Older builds may discard optional audio references when they save; export notebook JSON and WAVs before downgrading.

Phase 3B3 should use a versioned manifest containing original interview identity, recording UUID, format/sample count, WAV digest, relative archive entry and each segment's sample bounds. Restore must validate archive paths/sizes/hashes, map copied interview/recording IDs together, stage files, and commit associations transactionally with rollback. This is a future contract outline; combined backup/restore is not implemented here.

## CI trigger scope

The task branch keeps all five job names and PR triggers without a base-branch filter, and limits branch push CI to `main`. Concurrency still cancels obsolete runs within a PR. Publishing a new feature branch has no push workflow; opening its Draft PR should create one `pull_request: opened` run. Later updates to that PR should create one `pull_request: synchronize` run per push.

The existing recovery/3A/3B1 ancestors retain their own workflow versions. Their configuration is not changed by this child PR. In particular, pushes to `recovery/complete-source` can still start both push and PR runs until that branch adopts the trigger change. No ancestor branches, PR bases, required-check settings or protections are changed here; integrating one isolated CI commit later is preferable to rewriting the stack or repeatedly pushing ancestors. No checks were removed or renamed, so this trigger-only reduction preserves check-name compatibility; repository protection settings remain outside this task.
